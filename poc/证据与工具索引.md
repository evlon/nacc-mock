## 二、关键证据详解

### 证据 1：登录密码是 base64(明文)，不是 AES（2026-10-12 抓包纠正）

**背景**：早期逆向误判登录密码为 AES-128-CBC（key=`1234567890abcdef`），
导致脚本用 AES 加密后提交，服务器一直返回 `0x80000058 密码错误`。

**证据（前端 auth/password 请求体，抓包实测）**：

```
POST /nac/user/auth/password?t=<毫秒时间戳>
body:
  username=<NAC_USERNAME_B64>           ← base64("<NAC_USERNAME>")
  password=<NAC_PASSWORD_B64>               ← base64("<NAC_PASSWORD>")，即明文直接 base64
  verifycode=&challenge=&terminal=&rmbpwd_browser=&encode=1&type=&auto_login=
  realip=<WAN_IP>
  access_net_flag=1
  terminal_type=windows
  onlineaddrs=g~3xxxi<WAN_IP>
```

**关键字段对比**：

| 字段 | 早期（错误） | 正确 |
|------|-------------|------|
| password | AES-128-CBC 密文 | base64(明文) |
| username | 明文 | base64(明文) |
| realip | 空 | `<WAN_IP>` |
| access_net_flag | ❌ 缺失 | 1 |
| onlineaddrs | 空 | `g~3xxxi<WAN_IP>` |

**结论**：
- AES-128-CBC（Ghidra `FUN_00549af0`/`FUN_005499c0`、前端 `O()` 函数）
  是客户端用于**解密服务器下发配置（如 VSG_PWD cookie）**的，与登录密码无关。
- 登录密码就是 `base64(明文)`，HTTPS 下仍有明文泄露风险（base64 可逆）。

**验证工具**：`verify_pwd_shell.sh`
```sh
sh verify_pwd_shell.sh
# 期望输出：明文 <NAC_PASSWORD> → base64 后 = <NAC_PASSWORD_B64>
```

### 证据 2：合规签名 = AES-192-ECB（100% 命中）

**签名算法**：
```
明文 = sprintf("%d %s %d", time()+5, sessionid, flag) + 30个空格
flag = 7（autologin_flag=="1"）否则 5
密钥 = base64_decode(pskey)  # 24 字节
加密 = AES-192-ECB（明文零填充 \x00 到 16 对齐）+ Base64
```

**证据（固定 ts=1791604916，flag=5 实测比对）**：

```
结果: <SIG_CIPHERTEXT>
期望: <SIG_CIPHERTEXT>
OK: 签名算法一致
```

**关键坑（必须零填充，不能 PKCS7/nopad）**：
- 明文长度 63 字节，需补 1 个 `\x00` 到 64（16 对齐）；
- shell 变量不能存 NUL 字节 → 用 hex 拼接 + `xxd -r -p` 还原。

**验证工具**：
- `verify_signature.py`（Python 参考实现）
- `verify_sig_shell.sh`（shell 版，路由器环境可用）

### 证据 3：pskey 账号级、明文下发

**证据（access_policy.json 响应）**：

```json
{
  "device_id": "3469",
  "is_installed_client": "0",
  "is_registered": "1",
  "is_verified": "1",
  "client_policy_xml": "... pskey=\"<NAC_PSKEY>\" ..."
}
```

**关键发现**：
- pskey 嵌在 `client_policy_xml` 的 `POLICY` 标签里，**顶层 JSON 无单独 pskey 字段**；
- pskey 是**账号级**（不同设备/会话复用同一 pskey），不随 device_id 变化；
- pskey 明文下发（HTTPS 传输，但响应体里直接可见），是上报签名的 AES-192 密钥。

**验证方法**（手动）：
```sh
curl -sk -H "Cookie: VSG_SESSIONID=<SESSIONID>" \
  "https://<NAC_SERVER_IP>/nac/user/check/access_policy.json" \
  | grep -oE 'pskey=\\"[^\\"]*\\"'
```

### 证据 4：准入判定在服务器侧，本地客户端非必要前提

**证据（access_policy.json 响应，is_installed_client=0 时）**：

```json
{
  "is_verified": "1",          ← 服务器已判定"合规验证通过"
  "is_installed_client": "0",  ← 但未安装客户端！
  "is_registered": "1",
  "pskey": "<NAC_PSKEY>"       ← 仍下发完整准入凭据
}
```

**结论**：`is_verified=1` 与 `is_installed_client=0` 并存，证明服务器侧的
"设备注册 + 合规验证"已完成，本地客户端只是"终端执行器"（采集合规数据 +
本地拦截 + 代答 EAP），**不是准入判定的必要前提**。

**验证工具**：`nac_client_mvp.py`（复用 sessionid 模式，跳过登录直接上报）

### 证据 5：复用 sessionid 上报 score=90 → fwdsa=3（放行）

**证据（check/result 响应）**：

```json
{
  "code": "0x00000000",
  "msg": "成功",
  "result": {
    "device_id": "3469",
    "session_id": "<SESSIONID_PLACEHOLDER>",
    "fwdsa": "3",          ← 放行（此前拦截为 12，未放行为 0）
    "under_nat": "0",
    "nat_qos_dscp": "0",
    "nat_ip_ttl": "0"
  }
}
```

**结论**：服务器完全信任客户端上报，不校验源 IP / 设备绑定。
`fwdsa` 字段语义：`12`=拦截 / `0`=未放行 / `3`=放行。

**验证工具**：`nac_client_mvp.py`（Windows）/ `nac_openwrt.sh`（路由器）

### 证据 6：路由器自主登录闭环（本次核心成果）

**环境**：CUDY TR3000（K-WRT 25.12，aarch64），WAN 口直连公司网络。

**完整 run 实测输出（节选）**：

```
登录响应: { "code": "0x00000000", "msg": "成功" }
登录成功，sessionid=<SESSIONID_PLACEHOLDER>
获取策略成功: pskey=(已存) device_id=3469
上报合规 score=90 ...
result 响应: { "code": "0x00000000", "msg": "成功", ..., "fwdsa": "3" }
解析: fwdsa=3 under_nat=0 nat_ip_ttl=0 nat_qos_dscp=0
进入心跳循环（每 10s 心跳，每 120s 重报）
```

**结论**：路由器可完全自主完成「登录 → 拿 sessionid → 拿 pskey/device_id →
上报合规 → fwdsa=3 放行 → 心跳循环」，无需依赖真机或手动复用 sessionid。

**验证工具**：`nac_openwrt.sh`（子命令 login/policy/report/run/status）

### 证据 7：内网设备出网被路由器 SNAT（无需额外打水印）

**证据（路由器 conntrack 表）**：

```
src=<LAN_IP>  dst=<PUBLIC_DST_IP> ... → src=<PUBLIC_DST_IP> dst=<WAN_IP>   (SNAT!)
src=<LAN_IP>  dst=<PUBLIC_DST_IP> ... → src=<PUBLIC_DST_IP> dst=<WAN_IP> (SNAT!)
src=<LAN_IP> dst=<PUBLIC_DST_IP> ...   → src=<PUBLIC_DST_IP> dst=<WAN_IP>     (SNAT!)
```

**机制**：`srcnat_wan` 链（fw4 fullcone NAT）把内网设备出网流量的源 IP
统一改写为路由器 WAN 口 IP。公司网络/NAC 服务器只看到**一个设备**（路由器），
看不到内网设备。

**结论**：场景 A（路由器 WAN 直连公司）下，内网设备无需打 TTL 水印——
它们被 SNAT 成"已放行"的路由器。水印仅在场景 B（路由器自己被放在另一个
NAT 后面）才需要。

**验证方法**：
```sh
cat /proc/net/nf_conntrack | grep "192.168.3\."   # 看回程目标是否变成 <WAN_IP>
```

---

### 证据 8：水印仅 under_nat=1 时下发

**机制**：服务器在 `check/result` 响应里下发水印参数，仅当：
- `under_nat=1`（设备在 NAT 后面）
- `nat_traversal=1`（服务器开启 NAT 穿透）

**场景对比**：

| 场景 | under_nat | nat_traversal | 是否下发水印 |
|------|-----------|---------------|-------------|
| A：路由器 WAN 直连公司 | 0 | 0 | ❌ 不下发 |
| B：路由器在另一 NAT 后面 | 1 | 1 | ✅ 下发 TTL/DSCP |

**验证工具**：`verify_watermark.py`（检查 TTL/DSCP 是否打上）
